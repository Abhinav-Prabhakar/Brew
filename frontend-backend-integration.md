## 2. Where things stand (facts)

### Backend: done, tested, live
- **Start it:** `uv run brew-api` on port 8000; OpenAPI at `/docs`. CORS is enabled.
- **Live, no speeds:**
  - The café runs in **real time** (`BREW_LIVE_RATE=1.0`).
  - Create a world with `POST /api/v1/worlds {"policy":"D","clock":"wall"}`. It starts on today's date and
    fast-forwards to the current time in Asia/Kolkata. `POST /worlds/{id}/control {"action":"play"}` then keeps it
    locked to the wall clock.
  - Controls are `play`, `pause` and `step` (step is for tests and debugging). There are no 1×/10×/60× speeds.
  - For fast deterministic tests use `clock:"open"` plus `step`, or `BREW_LIVE_RATE=…` (dev only).
- **Hydration:** `GET /worlds/{id}/state` returns one snapshot with world, clock, weather, KPIs, menu, Replate
  listings, combos, rail (orders and batches), board, customers (state, appearance seeds, patience, table), tables,
  fridge, shelf, staff, equipment, policy, strategy and `last_seq`.
- **Stream:** `WS /api/v1/ws/worlds/{id}?since_seq=<last_seq>` sends batched frames
  `{"frame":n,"events":[{seq,sim_s,t,type,data},…]}` every 50–100 ms, with a 10k ring buffer for reconnect replay,
  resync and heartbeat. `{"op":"subscribe","types":[…]}` is optional.
- **The 71 event types:**
  - time and weather: `clock.tick`, `weather.changed`, `day.started`/`ended`
  - customers: `customer.*` (arrived, queued, balked, ordering, waiting, patience, reneged, seated, eating, lingering,
    paying, left)
  - orders and the rail: `order.*` (placed, accepted, rejected, progress, ready, served, voided), `rail.reordered`,
    `batch.formed`/`started`
  - delivery and payment: `bag.shelved`, `rider.*`, `receipt.printed`, `payment.received`, `review.posted`
  - menu: `price.changed` (also `sku:"combo:<id>"` for combos), `menu.featured`/`hidden`/`restored`, `replate.*`
    (listed, marked_down, sold, retired, mode)
  - stock: `stock.changed`, `lot.opened`/`expired`/`donated`, `po.created`/`received`
  - kitchen: `task.started`/`finished`, `prep.*`, `staff.*` (clocked_in/out, break_started/ended, absent, late),
    `equipment.down`/`up`
  - management: `kpi.tick` (every 5 sim-min), `decision.made`, `bottleneck.changed`, `chaos.triggered`/`resolved`,
    `strategy.changed`, `policy.changed`, `throttle.changed`, `investment.delivered`, `action.applied`
  - Every payload is a pydantic model in `src/brew/events/schema.py`; the JSON schema is at `GET /events/schema`.
- **Read models:** `/menu`, `/combos`, `/replate`, `/orders`, `/rail`, `/board`, `/customers`, `/tables`,
  `/inventory`, `/inventory/{key}/lots`, `/fridge`, `/shelf`, `/staff`, `/equipment`, `/kpis`, `/impact`, `/reviews`,
  `/receipts/{order_no}`, `/decisions`, `/decisions/{id}/explain`, `/disruptions`, `/forecast`, `/bottlenecks`,
  `/advisor`, `/invest`, `/arena` (async job), `/models`.
- **Actions:** `POST /worlds/{id}/actions {kind, …}` with these kinds:
  - `serve_order`, `bump_order`, `restock_fridge`
  - `set_price` (charter-checked; 422 on violation), `feature_item`, `hide_item`, `throttle`
  - `place_po`, `premake`, `replate_list`, `replate_mode`
  - `POST /worlds/{id}/chaos {kind,…}` triggers a disruption.
  - Errors use one envelope: `{"error":{code,message,details}}`.
- **Policies:** A naive, B heuristic, C optimiser, D learned RL (ONNX champion `models/rl_policy/D/full-5033b06`), E
  oracle. **The demo world runs D.** Final 10-seed × 7-day arena, per day: A ₹62.1k, B ₹73.5k, C ₹96.9k, **D ₹104.9k**.
  The full metrics are in `docs/training/full-20261005/metrics.json`.

## 3. Design rules (keep them consistent)
- **Tokens:**
  - ink `#1d1a1c`, paper `#fbf7f1`, ground `#efe6dc`

- **Fonts:** Gochi Hand (titles and big numbers), Patrick Hand (body), Caveat (handwritten notes and reasons), Courier
  Prime (receipts).
- **Line work:** 2.5–3.5 px ink strokes, round joins; the SVG `#wob` turbulence filter for hand-drawn wobble;
  `.card` radii `255px 18px 225px 18px/18px 225px 18px 255px`; offset ink shadow `4px 5px 0 var(--ink)`; paper grain
  overlay.
- **Motion:** nothing pops; numbers roll; tickets slide; prices are struck through in ink then rewritten (see
  `menu.js`); honour `prefers-reduced-motion`.
- **Doodles:** reuse the `<symbol>`s defined in `lobby.js`, `kitchen.js` and `pantry.js` (latte, coldbrew, croissant,
  cake, toast, matcha, k-*, p-*). New doodles must match: same stroke weights, flat fills from the tokens, slight
  wobble.

## 4. Phase A: the test suite (do this first)
Today nothing on the frontend is tested and everything is mocked, so you can't tell whether wiring works. Build the
tests that define it before writing integration code. Explore and decide the details yourself; the direction is:

1. **One toolchain.** Prefer **Python Playwright via uv** (`uv add --dev pytest-playwright`, then
   `uv run playwright install chromium`) so frontend tests run under the same `uv run pytest`. Add Node and Vitest
   only if you find a strong reason, and document it.
2. **Golden event streams (fixtures).**
   - Write `scripts/record_stream.py`. It runs the real backend headless (`clock:"open"`, fixed seed, policy D, plus a
     scripted chaos event) and records the hydration snapshot and the full event stream for a slice of a day (for
     example 07:55–10:30, covering the morning rush) to `tests/fixtures/streams/*.jsonl`.
   - These fixtures are the contract between backend and frontend. Regenerate them when events change; a test fails
     if a fixture is stale against `/events/schema`.
3. **Contract tests (backend side).**
   - Every event in the fixtures validates against its schema.
   - Every event type the frontend subscribes to exists.
   - The hydration snapshot contains every field each room reads.
   - Write a machine-readable **`design/contract.json`**: event type → the frontend handler(s) → which visual. Assert
     coverage: every event in backend.md §6.3 is either handled or explicitly listed as ignored.
4. **Frontend state tests (pure, no backend).**
   - Refactor so that each room has a **pure state reducer**: `(state, event) → state`.
   - Feed the golden fixtures through it in a headless page (`page.evaluate`) and assert the resulting state: tickets
     on the rail, batch groups, customers and their states, prices, rescue listings, combos, crew status, station
     loads, lots, KPIs.
   - This is where most tests should live: fast and deterministic.
5. **Rendering tests.**
   - Load `design/brew.html` with a `ReplaySource` that plays a fixture at high speed.
   - Assert the DOM/SVG reflects state: ticket count and order numbers, the price text in the menu book, the profit
     figure, the station LED colours, the pantry lot freshness classes. Then check the screens never show a mock
     value.
   - Write a **no-mock assertion**: a test that fails if any hard-coded mock string ("#041", "asha", "₹18,420",
     "08:42") still renders once a real stream is connected.
6. **End-to-end tests (real backend).**
   - Start `brew-api` in-process or as a subprocess with `BREW_LIVE_RATE` high (dev only) or `step`-driven, and
     connect the real page.
   - Check: the WebSocket connects; hydration is right; events flow; actions round-trip (serve an order → its ticket
     tears off; set a price → the menu book rewrites it; trigger chaos → the kitchen chaos card updates); reconnect
     with `since_seq` resumes without gaps or duplicates.
7. **Visual regression.** Take Playwright screenshots per room at fixed fixture timestamps and diff them with a
   tolerance, so the hand-drawn look doesn't drift. Keep the baselines in `tests/visual/`.
8. **Performance guard (basic).** Measure frame time while replaying a busy fixture. Fail if the p95 frame exceeds a
   generous bound for now; the 16 ms target is enforced in the polish phase.
9. **CI.** Add a GitHub Actions workflow for the backend tests, ruff, mypy and the frontend tests (Playwright,
   Chromium, headless).

Commit the harness first, then add tests incrementally. Most of this is not UI design, so **delegate it to Sonnet 5.5
sub-agents** and review it yourself.

## 5. Phase B: integration
**Target architecture:**
```
WsSource (real) | ReplaySource (fixtures/demo fallback) | MockSource (dev only)
        └──────────────► bus (window.BREW_LIVE.on/emit; same contract menu.js already uses)
                              ├─► store: hydrate(snapshot) + reduce(event)   (pure, tested)
                              └─► room renderers (lobby, kitchen, pantry, HUD, menu book) subscribe and animate diffs
```
1. **Client layer** (`design/live/`):
   - a `WsSource` with hydration, `since_seq` resume, backoff reconnect, heartbeat and a `lagging` flag;
   - a `ReplaySource` for fixtures and an offline demo fallback;
   - a REST client for actions;
   - a boot flow: find or create the demo world (`policy D`, `clock wall`) → play → hydrate → stream.
2. **Turn the static SVG strings into renderers.** Keep the art. Split each room into a static backdrop (walls,
   counter, equipment: drawn once) and dynamic layers (tickets, customers, crew, cards, lots) rendered from state with
   keyed diffing, so elements enter, move and leave with the design's motion.
3. **Procedural characters.** `customer.arrived` carries persona and `appearance_seeds`. Build a doodle generator in
   the lobby style (head, eyes, brows, mouth, blush, hair and outfit by persona and seed) so every customer looks
   hand-drawn and stable across reloads. The crew comes from `/staff`.
4. **Wire every surface.** The gaps below are what's missing today for real integration. Close each one, adding
   backend endpoints or events where needed (delegate those to sub-agents, update backend.md and test them).
